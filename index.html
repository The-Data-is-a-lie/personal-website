01Why it exists

There was essentially no real Pathfinder 1e character generator. A few very basic ones existed, but they did a small fraction of the work — roll some numbers, then hand the actual character-building back to you. Nothing produced a finished, playable sheet.

And nothing came close to the rules we actually play with. Rolling a character by hand took an evening; I wanted one in seconds. So I went looking for the tool, found nothing that did the job, and wrote it myself.

02Making every character legal — and worth playing

Randomness is the easy part. The hard part is guaranteeing that every character the generator can possibly produce satisfies every rule in the system, 100% of the time — and that it's a character someone would actually want to play rather than statistical garbage. Those are two separate problems, and the second one is harder.

Pathfinder 1e is one of the most mechanically complex TTRPG systems in existence, and its options interlock. Feats gate feats — Combat Expertise gates Improved Trip. Class features gate options. Ability scores gate prerequisites. Skills gate unlocks. Maneuvers gate higher-discipline maneuvers. Picking randomly from a flat list produces an illegal sheet almost every time.

The consequence is retroactive invalidation: a choice made at level 13 can invalidate one made at level 3, because ability scores, class features and prerequisites all shift underneath earlier picks. So selection can't be greedy. It has to validate the whole build, backtrack out of dead ends, re-check, and still terminate — which means the search has to be bounded rather than left to thrash.

And legal isn't sufficient. A sheet can satisfy every prerequisite and still be unplayable — a melee build with no Strength, feats that support nothing the class does. It has to come out coherent: stats that support the feats, feats that support the class.

03Then: two more rule systems, and our own

Handling base Pathfinder 1e was only the first half. We don't play stock — every character at our table uses two complete third-party systems, Path of War (initiating classes and maneuvers) and Spheres of Power/Might (a talent-based replacement for both casting and combat), on top of a house-rule layer we'd built up over years: feat-tax exemptions, mechanical flaws, trainers, an expanded profession sub-system, skill unlocks.

Those additions were, by themselves, considerably more work than supporting the base system. Neither third-party system was designed to coexist with the other, and both replace core subsystems rather than extending them — so the generator has to know which rule wins where: how a Spheres caster's tradition interacts with a Path of War initiator's recovery, which class features get overwritten by a sphere package, how to hold two entirely different resource economies on one sheet.

The house rules then change what "legal" even means. Feat-tax exemptions remove edges from the prerequisite graph, flaws trade penalties for extra picks, trainers gate options behind in-world access. Legality stops being a fixed property of the rulebook and becomes a function of the configuration you generated with. Keeping that layer separable is what makes the tool usable by anyone who isn't at my table.

Each system also brought its own data corpus. The indexed pools the generator selects from now run to 8,816 feats, 6,035 items and 758 class-and-archetype entries — every one of which had to be machine-readable in the same shape before any of it could be validated.

04The front end I hadn't planned for

Finishing the backend didn't finish the project. I had a service that could produce a correct character and nowhere to show it — and handing someone a JSON blob isn't a tool. After learning Python from scratch and building the generator core, I still needed somewhere the output could actually live.

So the front end became FoundryVTT, the virtual tabletop my friends and I already played in. That meant learning JavaScript from scratch, and learning the internals of a large application I hadn't written: its data model, its hooks, how actors and items are structured, how to write back a fully populated sheet without corrupting it. The module collects twelve inputs in-app, calls the Flask service, and writes back a finished actor — items, spells, feats and all.

It's published on the official FoundryVTT package registry and has been in production since 2023. That's the part I'm actually proud of: not that it works on my machine, but that it's installable by strangers and has been in continuous use for three years, which is a very different bar.

05What I'd do differently

At the start I didn't know what I was doing. I began by copying a GitHub repo and iterating on it, and every basic change took far longer than it should have because I was working inside someone else's structure without really understanding it. Eventually I got fed up and rebuilt the whole thing from scratch — which was the right call, just much later than it should have come.

So the main thing I'd change is scoping. I'd map the project out before writing anything: an explicit diagram of what it needed to do, what data it needed, and what the pieces were. Almost all of the rework traced back to not having that picture and figuring it out as I went instead.

Smaller ones, all still true: model the prerequisite graph explicitly from day one rather than letting validation logic scatter across every module that needs it; treat the data pipeline as the foundation it turned out to be instead of a chore; and write property-based tests over legality — "no generated character ever violates a prerequisite" is exactly the kind of invariant that deserves a fuzzer rather than a handful of examples.
